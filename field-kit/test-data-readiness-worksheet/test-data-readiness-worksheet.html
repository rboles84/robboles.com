Test Data Readiness Worksheet

Use this before a smoke or E2E path depends on data nobody can explain. Name the source, owner, refresh, reset, mutation, cleanup, and staleness signals before the suite starts manufacturing noise.

Type into the fields, then print or save as PDF. The button disappears from the printed copy. This file does not save your answers after you close the tab.

Journey and environment

Readiness questions

Fill this for one critical path. The goal is not to document every record in the environment. The goal is to decide whether this path has data reliable enough for the test result to mean something.

Data source

Does this path use shared seed data, environment-specific data, dynamically created data, imported production-like data, or a mix?

Environment alignment

Do dev, QA, UAT, and upper non-prod environments share the same data source or at least the same data contract where they can?

Known-good smoke data

Which records, users, accounts, policies, orders, or states are trusted enough for a smoke path?

Dynamic data rule

Which data should tests create dynamically, and what setup cost is acceptable before the test stops being a useful smoke or E2E signal?

Safe mutation

Which records are safe to mutate, which must stay read-only, and which need to reset after the run?

Refresh cadence

How often is the data refreshed, who owns the refresh, and how does the team know a refresh changed the test assumptions?

Reset and repair path

When a required record is missing, stale, or dirty, who can reset or repair it without guessing?

Junk-data cleanup

What does automation create, what does manual testing leave behind, and what gets cleaned up on a schedule?

Staleness signal

How will the team know data is stale before the full suite fails?

Escalation rule

If data blocks a run, who decides whether the result is invalid, rerunnable, or a release-confidence issue?

If the worksheet has too many blank owner fields, the problem is not the form. The data path is not owned yet.

Failure buckets

Bucket Use when First move
Source mismatch Environments do not share the same data source or contract. Document the difference and decide whether it is intentional.
Stale data The record exists, but no longer matches the product or rule assumption. Refresh, repair, or remove the record from the trusted path.
Unsafe mutation A test changes shared data and leaves later runs in a different state. Move to fresh-created data, add reset, or mark the record read-only.
Junk accumulation Old manual and automated runs create enough noise to distort setup and triage. Create cleanup rules and a cadence, not a one-time purge.
Ownership gap The data problem is real, but nobody owns source, refresh, reset, or cleanup. Name an owner before adding more defensive automation.

Watch out: dynamic data is useful. Do not use this worksheet to ban it. Use it to tell the difference between deliberate dynamic setup and expensive compensation for unowned environments.

The gut-check line

If the smoke test fails, can the team tell whether the data is missing, stale, dirty, mutated, or genuinely exposing a product defect? If not, the data layer is not ready enough for the result to mean what people think it means.
