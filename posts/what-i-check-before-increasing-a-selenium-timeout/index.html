What I Check When a Test Passes Locally and Fails in CI

A local pass and a CI failure are two observations under different conditions. Compare the evidence, readiness, data, and execution before changing the timeout.

Sep 14, 20267 min readQA Field Guide
CI/CDFlaky TestsTest Triage

● Last verified Sep 14, 2026

Before rerunning, decide what the next result needs to tell you.

"It passes locally" is useful information. It gives me a comparison. A local pass and a CI failure are two observations made under different conditions. Before changing the timeout, I want to know which difference mattered.

My nightly runs fail often enough that I have to ask what changed beyond the code. A test runs one night, then Selenium times out between steps three and four of the same form the next night. That's still happening as I write this in September 2026.

The browser might be different. The data might have been used already. Several tests might be doing the same thing at once. The runner and browser might be in different places. Extra latency is possible, but I don't want to decide that's the cause before looking. I can call the test flaky. I still have to figure out why it failed.

Preserve the Crime Scene

Before a rerun, save the original failure. A rerun changes the evidence surface, and the newest result tends to take over the conversation. Get the original exception, the last successful action, and what the test expected to happen next. Keep the screenshot or video alongside the command log. Include the timestamp and session or run ID so someone else can find the same evidence.

The Timeout Probably Didn't Kill Your Test

A timeout tells me something didn't finish within the time allowed. It tells me where observation stopped, not necessarily where the failure started. Step four timing out doesn't prove step four was slow. Step three may not have saved, navigation may have failed, the data may be wrong, or the test may be waiting for the wrong state.

Waiting longer for the wrong state is still waiting for the wrong state.

Start with the evidence. Was the action sent? Did the application accept it? What was on the screen when the test stopped? Those answers determine whether I should be looking at the test or talking to someone who owns the application.

Don't Test the Commute When You Care About the Destination

One of my first questions is whether we can bypass the earlier form for this test. If I'm testing whether the hotel room shower works, I don't need to reenact the flight, rental-car pickup, check-in, and elevator ride every time.

Suppose we're checking something that happens after submission. We may be clicking through three screens to get a record into the state we need. If a supported API can create a valid record in that state, use it for setup and start the UI test closer to the behavior being checked. Selenium recommends preparing application state outside the browser.

But if we're testing the transition from step three to step four, bypassing it defeats the purpose. Keep that journey covered. The question is which tests need to travel through it, and which ones repeat it because that's how they were originally written.

Check the resulting data, too. A shortcut that creates an incomplete record trades one problem for another. I want the setup to produce a valid starting point that the test can verify before continuing.

Don't wait for time. Wait for meaning.

Can we add a wait? Sure. What would we wait for?

A visible dropdown might still be missing its options. A button might be enabled while a request is still running. The page can look finished enough for a screenshot and still be missing what the next action needs.

With Selenium, an explicit wait lets us check a specific condition. An implicit wait deals with finding elements. I wouldn't stack them together; Selenium warns that mixing them can produce unpredictable timeout durations.

Newer tooling handles more of this automatically. Playwright checks things such as visibility, stability, and whether an element can receive the click. Its auto-waiting behavior removes a lot of checks we'd otherwise write ourselves.

That still leaves application behavior to understand. Playwright documents a case where controls appear usable before the page has attached their event handlers. The test can click successfully and nothing happens. Its hydration guidance recommends fixing the application's readiness behavior, rather than relying on the test to happen to be slow enough.

So I want a condition tied to the next action: the expected options have arrived, the previous save has completed, the correct record is displayed, or the required control is ready for the next action. Pick the condition the scenario actually needs. We don't need a general-purpose wait for everything on every page.

Your Assertion Is Not a Sleep Function

I also look for something on the page we can validate while the rest loads. A value carried over from the previous step may already be available. Checking it could tell us whether the transition preserved the right information.

That's useful if it belongs in this test. Adding an unrelated assertion because it happens to burn time creates hidden timing coupling. Remove it later and the original failure comes back.

An extra click can do more damage. It might move focus, trigger validation, start another request, or change the application sequence. Keep the action if it's part of the intended workflow. Otherwise, wait for the state we need.

Change One Variable, Sherlock

This is the boring part of being a detective: change one useful thing at a time.

CI and a remote browser service aren't the same thing. The CI job runs the test code; the browser may run on that machine or somewhere else. That distinction helps locate the delay.

Use the same application build and browser version where practical. Match the viewport, account permissions, and starting data. Then compare the case locally with the case running by itself in CI. If the browser is remote, keep its session details with the test results.

If it fails by itself, inspect the commands around the failure and the application's requests. A browser that's waiting for a response and a runner that's struggling to reach the browser need different fixes.

Next, compare that isolated CI run with the normal parallel run. If the failure appears only alongside other tests, investigate what those tests share. Sauce Labs' troubleshooting documentation covers session ownership, logging, and failures that emerge as parallelism increases.

This takes more work than adding ten seconds to a timeout. It also gives the team a specific difference to investigate.

Your Test Data Has Roommates

Same code doesn't mean the same starting conditions. A record that effectively lives alone during a local run may have roommates in CI. A previous run may have changed it. Another test may be using the same account. Cleanup may have failed before the next run started. Multiple workers may be sharing the same resources.

Look at the record's state at the moment of failure. Don't assume it's still in the state it had when somebody created the test.

Separate data per run helps where it's practical, along with cleanup that doesn't remove another run's records. Selenium's shared-state guidance makes the same recommendation. Shared data isn't automatically wrong, but its mutation rules need to be clear: document what can change and which tests are allowed to change it.

Stop Asking the Rerun Whether It Passes

A passing rerun is worth recording. It doesn't explain the earlier failure. Give the rerun a question and record the chain: hypothesis → one meaningful change → result → interpretation.

Suspect shared data? Use a fresh record. Suspect concurrency? Run an isolated worker. Suspect readiness? Wait for the required state. Record whether the result supports that explanation.

Fresh data plus a longer timeout plus lower concurrency plus another browser may produce PASS. That may restore green, but it doesn't tell us which explanation was correct.

A green build is an outcome. An explanation is knowledge.

Sometimes a longer timeout is the right adjustment. If we've measured the expected state arriving correctly after the current limit in a supported environment, we have a reason to change it. Keep the limit bounded and explain where the new value came from.

Also check whether that delay is acceptable for the product. A functional test waiting longer doesn't settle a response-time requirement. We may have found an application problem the test should continue to expose.

Leave Receipts

If someone else receives the failure, they shouldn't have to rediscover everything we've already learned. Here's a record you can copy into the ticket. Fill in what you know and leave the rest unanswered until you've checked it.

Before rerunning, put one sentence in that last section explaining what you're trying to learn. It gives the next result a job beyond turning the build green.

The goal isn't to make the red result disappear. It's to identify the changed condition that explains the failure well enough to decide whether the fix belongs in the test, the data, the environment, or the application.

Better tests. Better releases. Less theater.
